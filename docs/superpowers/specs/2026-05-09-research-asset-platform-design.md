# 企业内部科研资产平台设计方案

日期：2026-05-09

## 1. 背景

当前目录中已有一个单文件 HTML demo：`京津冀城市韧性_cloud_supabase_版本.html`。它验证了核心产品方向：团队成员可以上传空间数据，在地图上预览，并通过云端方式共享。

该 demo 的价值在于表达产品效果和业务需求，但它还不是可正式投入企业使用的工程项目。现状主要问题包括：

- 前端、业务逻辑、样式、地图逻辑、存储逻辑都集中在一个 HTML 文件中。
- 后端依赖 Supabase 免费版和浏览器端配置，难以支撑企业团队长期使用。
- 大量 GIS 解析发生在浏览器端，面对大文件、ArcGIS 常见导出格式和后台处理时扩展性不足。
- 缺少正式账号管理、审计日志、处理状态、部署方案和可维护的工程结构。

平台重构不应简单“修补 demo”，而应基于 demo 表达的用户体验，重新设计为可私有化部署、可上云部署、可长期扩展的企业内部科研资产平台。

## 2. 产品定位

平台定位为：企业内部科研资产平台。

一期核心是空间数据资源库，解决团队 ArcGIS/GIS 成果文件的统一上传、归档、检索、地图预览和原始文件下载。

二期核心是 AI 论文知识库，解决团队论文、报告等文字成果的统一入库、语义检索、可溯源问答和外部资料补充。

两个模块共享统一账号体系、文件存储、审计日志和系统配置，但业务处理链路保持独立，避免 GIS 数据处理与论文 RAG 流程互相耦合。

## 3. 目标用户与权限

目标规模为 20-50 人团队。

一期权限采用平台级登录模式：

- 只有授权账号可以进入平台。
- 登录后成员均可上传、下载、搜索和在线预览。
- 一期不做复杂的数据集级权限、部门权限或审批流。
- 系统保留上传人、上传时间、下载记录、处理记录和操作日志，为后续审计与权限扩展预留基础。

## 4. 总体架构

推荐路线为：自建轻量企业后端 + 对象存储 + PostgreSQL/PostGIS。

整体架构包括：

- Web 前端：提供登录、数据资源库、地图预览、上传入库、知识库问答等界面。
- API 后端：提供认证、文件上传、检索、下载、空间查询、文档问答等接口。
- PostgreSQL + PostGIS：保存用户、空间数据元信息、空间范围、行政区边界、标签、处理状态、审计日志和知识库元信息。
- 对象存储：保存原始上传文件和派生文件。可使用 MinIO 私有化部署，也可替换为阿里云 OSS、腾讯 COS、华为云 OBS 等。
- 后台任务队列：负责 GIS 文件识别、预览转换、文档解析、向量索引构建和外部资料补充。
- GIS 处理服务：基于 GDAL/OGR 等工具识别和转换 ArcGIS/GIS 常见格式。
- AI 服务适配层：接入在线大模型 API，并预留未来切换模型供应商或私有模型的能力。

部署方式以 Docker Compose 起步，后续可以迁移到云服务器或 Kubernetes。

## 5. 阶段一：空间数据资源库

### 5.1 核心目标

阶段一目标是把现有 demo 重构为可正式使用的企业内部 GIS 数据资源库。

核心用户流程：

1. 成员使用账号密码登录平台。
2. 进入数据资源库，上传 GIS 原始文件。
3. 上传时填写数据名称、所属项目或主题、标签、简短说明。
4. 后端保存原始文件。
5. 后端自动识别文件类型、坐标系、空间范围、字段信息和处理状态。
6. 系统生成用于在线地图预览的派生副本。
7. 其他成员可以通过关键词、上传人、上传时间、数据类型、主题和标签检索数据。
8. 成员可以在地图上点击行政区，查看覆盖该区域的已有研究数据。
9. 找到数据后，可以在线预览，也可以下载上传者的原始文件。

### 5.2 页面与功能

阶段一前端包括以下页面：

- 登录页：账号密码登录。
- 数据资源库：列表、搜索、筛选、上传入口、下载入口。
- 数据上传页或弹窗：选择文件并填写名称、主题、标签和说明。
- 数据详情页：展示元信息、字段信息、空间范围、处理状态、预览入口和原始文件下载入口。
- 地图预览工作台：临时加载数据，调整样式并查看空间分布。
- 行政区成果发现：点击行政区后显示该区域已有数据列表。

样式配置只作为临时预览能力，不作为一期核心协作对象保存。平台一期重点是数据共享，而不是协同制图。

### 5.3 文件格式策略

阶段一必须符合团队从 ArcMap/ArcGIS 直接导出的使用习惯。

用户侧支持格式描述为：

- Shapefile 压缩包：`.zip`
- ArcGIS 导出的栅格：`.tif/.tiff`
- ArcGIS 栅格配套文件包：可包含 `.tfw`、`.tif.aux.xml`、`.ovr`、`.prj`、`.xml` 等
- GeoJSON 或 JSON：`.geojson/.json`
- GeoPackage：`.gpkg`
- KML/KMZ：`.kml/.kmz`
- CSV 点位表：`.csv`

平台不要求使用者理解 GeoTIFF、COG、瓦片等内部技术概念。用户按 ArcMap/ArcGIS 的习惯上传，后端负责识别和规范化。

处理规则：

- Shapefile 要求 zip 上传，因为 Shapefile 是多文件组合。
- 平台检查 Shapefile zip 是否包含 `.shp/.shx/.dbf`，并尽量读取 `.prj/.cpg`。
- 如果缺少坐标系信息，系统提示用户补充或标记为待补充。
- TIFF 栅格可以单文件上传，也可以与配套文件一起打包上传。
- 如果 TIFF 内含空间参考，系统直接识别。
- 如果 TIFF 缺少空间参考，系统尝试读取配套文件；仍无法识别时，提示用户补充坐标系或标记为待补充。
- 原始文件永久保存，平台预览副本可随时重建。

### 5.4 空间检索

数据入库时，后端为每个空间数据提取空间范围，并保存到 PostGIS。

行政区边界也进入 PostGIS。一期默认支持京津冀，架构支持后续由管理员导入全国或其他区域行政区边界。

行政区点击查询流程：

1. 用户在地图上点击某个行政区。
2. 前端向后端提交行政区 ID。
3. 后端使用 PostGIS 空间相交查询，查找覆盖该行政区的数据。
4. 前端显示相关数据列表，包括名称、类型、上传人、主题、标签和预览/下载入口。

这个功能保留 demo 的核心亮点，但不再依赖前端临时加载所有行政区和所有数据。

### 5.5 数据可靠性

原始文件是主资产。平台必须保证：

- A 上传的数据，B 可以下载到 A 上传的原始文件。
- 预览副本只是派生缓存，损坏后可从原始文件重新生成。
- 数据处理失败不应导致原始文件丢失。
- 每个数据集有明确处理状态，例如待处理、处理中、处理成功、处理失败、缺少坐标系。

## 6. 阶段二：AI 论文知识库

### 6.1 核心目标

阶段二把平台扩展为团队内部研究助理。

知识库不是普通文件夹，也不是简单关键词搜索。它应基于团队论文和报告构建可溯源的问答系统，优先使用内部资料回答问题，并在内部资料不足时自动补充外部资料。

### 6.2 核心流程

1. 成员上传 PDF 或 Word 论文、报告。
2. 系统解析文档文本，提取标题、作者、年份、摘要、关键词和章节等信息。
3. 系统把文档拆成可检索片段，并保留来源研究和原文片段。
4. 用户用自然语言提问。
5. 系统先从内部知识库检索相关片段。
6. 如果内部资料不足，系统自动补充外部资料。
7. 大模型基于证据生成回答。
8. 回答明确区分团队内部依据和外部补充资料。
9. 回答附带来源研究标题和原文片段，方便核查。

示例问题：

- 团队现有研究中城市韧性指标有哪些？
- 哪些论文使用过空间计量模型？
- 京津冀韧性研究有哪些主要结论？
- 当前团队研究中常见的技术手段有哪些，分别在哪些研究中应用？

### 6.3 RAG 设计原则

知识库采用 RAG + 大模型推理。

关键原则：

- 先检索证据，再生成回答。
- 大模型不能凭空声称团队已有某项研究。
- 如果内部资料证据不足，必须明确说明内部知识库暂无充分依据。
- 外部资料作为补充时必须单独标注。
- 引用以研究标题和原文片段为主，页码可选，不作为一期硬性要求。

### 6.4 技术组成

知识库包括：

- 文档原文存对象存储。
- 文档元信息存 PostgreSQL。
- 文本片段存数据库。
- 向量索引用 pgvector 或独立向量库。
- 检索采用向量检索 + 关键词检索混合方式。
- 在线大模型 API 用于回答生成、问题改写、证据归纳和总结。
- 模型接入层保持可替换，避免绑定单一供应商。

一期支持 PDF 和 Word。架构预留 PPT、网页、政策文件等资料类型。

团队论文和已发表资料允许使用在线大模型 API 处理。系统仍保留敏感等级字段，为未来内部报告或未发表资料进入知识库时预留治理能力。

## 7. 分阶段交付

采用分阶段交付：

### 第一阶段：GIS 数据资源库

交付企业可用的数据共享平台：

- 登录
- 数据上传
- 元数据填写
- 原始文件保存与下载
- 后台 GIS 识别与处理
- 数据列表与检索
- 地图预览
- 行政区点击发现
- 审计日志
- Docker Compose 部署

### 第二阶段：AI 论文知识库

在第一阶段平台底座上增加：

- PDF/Word 上传
- 文档解析
- 文本切分
- 向量索引
- 关键词与语义检索
- AI 问答
- 来源研究和原文片段引用
- 外部资料自动补充

## 8. 明确暂不做的事项

一期不做：

- 复杂数据集级权限。
- 数据上传审批流。
- 保存地图项目和样式配置。
- 替代 ArcGIS 的专业制图能力。
- FileGDB 和超大栅格完整支持。
- 精确页码级论文引用。
- 私有化大模型部署。

这些能力可以作为后续增强项。

## 9. 成功标准

阶段一成功标准：

- 20-50 人团队可以用账号登录平台。
- 成员可以上传常见 ArcGIS/GIS 文件。
- 上传者原始文件可被其他成员下载。
- 系统能识别数据类型、空间范围和基础字段信息。
- 用户可以通过名称、上传人、时间、类型、主题和标签找到数据。
- 用户可以在地图中预览数据。
- 用户点击京津冀行政区后，可以看到覆盖该区域的已有数据成果。
- 平台可通过 Docker Compose 在服务器上部署。

阶段二成功标准：

- 成员可以上传团队论文和报告。
- 系统能解析正文并建立检索索引。
- 用户可以用自然语言提问。
- 回答优先基于内部论文和报告。
- 回答包含来源研究和原文片段。
- 内部资料不足时，系统可以自动补充外部资料，并清楚标注。

## 10. 后续步骤

本设计确认后，下一步应进入实施计划阶段，拆分第一阶段开发任务，包括：

- 工程初始化
- 数据库 schema
- 后端 API
- 对象存储
- GIS 后台处理
- 前端页面
- 地图预览
- 行政区空间查询
- 测试与部署
